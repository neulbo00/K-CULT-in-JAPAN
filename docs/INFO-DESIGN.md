# K-CULT in JAPAN 인포 디자인 가이드

## 1. 디자인 목표

K-CULT는 일본 내 K-POP·K-Music·K-Drama·K-Culture 이벤트를 한곳에서 파악하는 데이터 기반 정보 서비스다. 단순한 포스터형 인포그래픽보다 이벤트 규모, 시기별 흐름, 지역 분포, 다가오는 일정을 빠르게 탐색하는 대시보드를 지향한다.

핵심 콘셉트: **JAPAN HALLYU INTELLIGENCE**

## 2. 시각 디자인 시스템

- 테마: Dark Premium
- 배경: 상단은 딥 차콜 위에 은은한 레드 광원, 하단은 딥 네이비 위에 은은한 블루 광원이 이어지는 수직 그라데이션
- 패널: 배경보다 한 단계 밝은 네이비 차콜, 화면 아래쪽으로 갈수록 블루 기운을 아주 약하게 반영
- 포인트: 상단·브랜드·핵심 수치에는 K-CULT 레드, 하단의 지역·일정 영역에는 차분한 블루
- 컬러 흐름: 위쪽의 레드에서 아래쪽의 블루로 자연스럽게 이동하며, 경계가 띠처럼 보이지 않도록 저채도 광원과 어두운 중간색을 사용
- 가독성: 레드와 블루는 배경 장식 및 상태 구분용으로 제한하고 본문 텍스트 대비를 우선
- 보조 상태색: 성공·정상 상태에만 제한적으로 그린 사용
- 텍스트: 제목은 높은 대비, 설명과 보조 정보는 낮은 대비
- 숫자: 고정폭 숫자체를 사용해 통계값 비교를 쉽게 함
- 모서리: 카드와 입력 요소는 일관된 라운드 값 사용
- 모션: 데이터 표시를 방해하지 않는 짧은 전환만 사용하며 prefers-reduced-motion 준수

## 3. 정보 구조 및 화면 순서

### A. Global Header
- K-CULT 브랜드
- Overview / Trends / Regions / Schedule 앵커 메뉴
- 데이터 기준일 표시
- 모바일에서는 메뉴를 간결하게 축약

### B. Hero
- 핵심 문구: “한류의 흐름을 숫자와 일정으로 읽다.”
- 서비스가 다루는 정보 범위를 한 문장으로 설명
- 전체 이벤트 수와 데이터 기준일을 요약 표시

### C. Overview / Snapshot
- 전체 이벤트 수
- 이벤트 유형 수
- 카테고리 수
- 공개 일정 수
- 각 수치는 데이터 파일의 실제 값만 사용

### D. Trends
- 월별 이벤트 추이
- 이벤트 유형별 분포
- 한류 카테고리별 분포
- 주요 프로모터 TOP
- 집계 기준과 데이터 불일치 안내를 차트 가까이에 표시

### E. Regions
- 일본 8개 권역을 기준으로 지역별 분포 제공
- 권역별 이벤트 수와 비중을 지도 또는 막대 차트로 표시
- 지역 속성이 연결되기 전에는 임의의 수치나 가짜 지도를 표시하지 않고 준비 상태를 명확히 안내

### F. Schedule
- 다가오는 이벤트 목록
- 이벤트명 검색
- 이벤트 유형 필터
- 날짜, 종료일, 유형, 장소 등 실제 공개 가능한 필드를 단계적으로 추가
- 이벤트 상세 또는 공식 안내 링크가 확보된 경우에만 연결
- 미리보기 데이터와 전체 일정 데이터의 범위를 명확히 구분

### G. Footer
- 데이터 출처
- 최종 갱신일
- 운영 주체 및 저작권 표기

## 4. 반응형 기준

- Desktop: 넓은 화면에서 통계와 차트를 2~4열로 배치
- Tablet: 통계는 2열, 차트는 콘텐츠 우선순위에 따라 1~2열
- Mobile: 단일 열 중심, 검색창과 필터 조작을 쉽게 배치
- 작은 화면에서 차트 라벨과 숫자가 겹치지 않도록 축약 규칙 적용

## 5. 데이터 표현 원칙

1. Notion을 원본 데이터(Source of Truth)로 취급한다.
2. 웹페이지는 공개 허용 필드만 포함한 data.js를 읽는다.
3. 데이터가 없는 항목은 0으로 위장하지 않고 “데이터 준비 중”으로 표현한다.
4. 전체 이벤트 수, 유형 합계, 카테고리 합계, 월별 합계를 별도로 검증한다.
5. 통계의 집계 기준(공연 시작일, 이벤트 등록일 등)을 각 차트에 명시한다.
6. 일정 미리보기 건수를 전체 일정 건수처럼 표현하지 않는다.
7. 외부 링크와 상세 정보는 실제 URL 또는 검증된 데이터가 있을 때만 제공한다.

## 6. 현재 구현 상태와 후속 작업

| 영역 | 현재 상태 | 후속 작업 |
|---|---|---|
| Header / Hero | 기본 구현 | 브랜드·문구·기준일 표현 정리 |
| Snapshot | 기본 통계 구현 | 지표 정의와 단위 통일 |
| Trends | 월별·유형·카테고리·프로모터 차트 구현 | 집계 불일치 검증, 차트 접근성 개선 |
| Regions | 8개 권역 안내 상태 | Notion 지역 데이터 연결 후 실제 지도·통계 구현 |
| Schedule | 검색·유형 필터·24건 미리보기 | 전체 일정 연동, 장소·공식 링크·상세 정보 |
| Responsive | 기본 반응형 구현 | 실제 모바일 화면에서 간격·라벨 점검 |
| Data integrity | 일부 합계 점검 안내 | 자동 검증 실패 시 배포 중단 |

## 7. 개발 순서

1. 이 가이드를 디자인 기준으로 확정한다.
2. 현재 index.html의 시각적 일관성과 모바일 사용성을 정리한다.
3. Notion 데이터 필드와 공개용 data.js 스키마를 확정한다.
4. 통계 및 일정 데이터를 실제 원본과 대조한다.
5. 지역별 데이터와 전체 일정 목록을 연결한다.
6. 데이터 검증을 통과한 뒤 공개 배포한다.

## 8. 완료 기준

- Desktop과 Mobile에서 정보 위계가 명확하다.
- 모든 숫자와 차트가 실제 data.js 값에서 생성된다.
- 데이터 누락과 집계 불일치가 숨겨지지 않는다.
- 검색·필터가 키보드와 모바일에서도 사용할 수 있다.
- Notion API 키 등 비밀정보가 공개 저장소에 포함되지 않는다.
- main 및 공개 사이트 반영은 검증 후 별도로 진행한다.


## 9. Taegeuk Dark 테마 확정안

테마명: **K-CULT 2.0 · Taegeuk Dark**

태극의 레드와 블루를 화면 위아래의 빛으로 해석한다. 화면을 두 색으로 반분하지 않는다.

- 상단: 깊은 와인 레드와 저채도 레드 광원
- 중앙: 거의 검정에 가까운 차콜 블랙
- 하단: 딥 네이비와 은은한 블루 광원
- 카드·본문: 차분한 다크 패널, 흰색·회색 텍스트 중심
- 레드: 브랜드, 핵심 지표, 상단 시각적 기준점
- 블루: 지역 정보, 일정 탐색, 하단 섹션의 보조 강조
- 차트: 데이터 시리즈의 의미가 있을 때만 레드·블루를 구분해 사용

## 10. 기간 선택 기능

기본 기간은 실행 시점의 현재 연도로 설정한다. 선택지는 연도별, 전체, 직접 지정으로 구성한다.

기간 변경 시 Snapshot, 월별 추이, 유형, 카테고리, 프로모터, 지역 통계, 일정 목록이 동일한 기간 조건을 공유해야 한다.

- 연도 선택: 해당 연도 1월 1일~12월 31일
- 전체: 데이터가 보유한 전체 기간
- 직접 지정: 시작일과 종료일
- 여러 날에 걸친 이벤트: 이벤트 기간과 선택 기간이 하루라도 겹치면 포함
- 종료일이 없는 이벤트: 시작일을 종료일로 간주
- 기간 경계 계산: 시작일 <= 선택 종료일 AND (종료일 또는 시작일) >= 선택 시작일

### 데이터 준비 조건

현재 data.js에는 전체 월별 집계와 24건의 upcoming 미리보기만 있다. 이 구조만으로 과거 연도·사용자 지정 기간의 유형/카테고리/지역/일정 통계를 정확하게 다시 계산할 수 없다.

기간 선택 기능을 완성하기 전에 Notion에서 공개 가능한 이벤트별 레코드(시작일, 종료일, 유형, 카테고리, 지역, 공개 여부)를 data.js 또는 공개 데이터 API로 공급하도록 스키마를 확장해야 한다. 원본 이벤트 레코드가 제공되기 전에는 기간 선택 UI를 실제 동작하는 것처럼 표시하지 않는다.

## 11. 자동 데이터 동기화 목표 아키텍처

목표 흐름:

Notion 데이터베이스 → Notion Webhook → Cloudflare Worker → Notion API로 변경 데이터 재조회 → 공개 필드 검증 및 집계 → 캐시/공개 데이터 → K-CULT 페이지

설계 원칙:
- Notion API 토큰은 Worker의 비밀 환경변수에 보관하고 브라우저나 GitHub Pages에 노출하지 않는다.
- Webhook 수신은 변경 알림으로 취급하고, 알림 본문만으로 공개 데이터 원본을 갱신하지 않는다. API에서 최신 레코드를 다시 조회한다.
- Notion API 호출 제한을 고려해 변경분 동기화, 요청 병합, 재시도, 캐시를 설계한다.
- 공개 허용 필드만 응답하며 비공개 메모, 개인 정보, 내부 속성은 제외한다.
- Webhook 재전송, 중복 이벤트, 일시적 장애에 대비한 멱등 처리와 로그를 둔다.
- 공개 데이터 API에는 캐시와 마지막 성공 갱신 시각을 제공한다.
- 기존 Windows 로컬 동기화는 우선 안정화 경로로 유지하고, Worker 이전은 별도 검증 후 진행한다.

## 12. 기간 선택 및 자동화 완료 기준

- 현재 연도가 기본 선택된다.
- 전체·연도별·직접 지정 기간이 실제 이벤트 레코드와 연결된다.
- 기간 변경 시 모든 통계와 일정이 동일한 필터 기준으로 갱신된다.
- 기간과 겹치는 다일 이벤트가 경계일 기준으로 정확히 포함된다.
- 공개 API 응답에는 허용된 필드만 존재한다.
- Notion 토큰은 서버 측 비밀 저장소에만 존재한다.
- Webhook 재시도·중복·오류 상황이 로그로 추적된다.
